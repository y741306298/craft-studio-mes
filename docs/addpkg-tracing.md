# addPkg 日志跟踪

新增日志从部署后生效。送货上门、自定义物流、快递100和聚单平台共用同一套跟踪。

先按订单号查询：

```bash
rg -n -F 'orderId=2115786287824351234' application.log
```

同一订单可能多次打包。找到对应的 `addPkg开始` 后，复制该条日志中的 `traceId` 查询单次请求：

```bash
rg -n -F 'traceId=实际值' application.log
```

主要日志：

- `addPkg开始`：请求开始，含订单号、traceId、物流类型和请求零件项数。
- `addPkg阶段开始/完成`：含 stage，完成时含 elapsedMs。没有完成记录的阶段可用于定位正在等待的操作。
- `addPkg包裹已保存`：包裹记录已保存，含 pkgId；后续生产件更新仍可能失败。
- `addPkg业务完成`：打包业务已完成，Controller 可能仍在构建二维码和打印响应。
- `addPkg成功`：Controller 已构建打印响应，含 pkgId 和 totalMs；不代表客户端已收到响应或纸质标签已打印。
- `addPkg失败`：含具体失败阶段、totalMs、异常类型和堆栈；如果包裹已经保存，也会记录 pkgId，便于核对部分成功的状态。

主要阶段包括查询生产件、查询订单、生成备注、创建包裹、更新打包状态、查询订单项完成数量、批量更新生产件、刷新订单项完成状态、批量更新订单项、构建打印响应。快递100和聚单平台另有对应分支阶段。嵌套阶段耗时有重叠，不应相加；请求总耗时以 totalMs 为准。

Controller 的 totalMs 包含业务处理与打印响应构建，不包含 Controller 之前的反序列化、之后的 HTTP 序列化和网络传输。直接调用应用服务时，成功日志只涵盖业务处理。

完成状态判断按去重后的订单项 ID 批量查询，不再在生产件循环中调用 findByOrderItemId。订单项不存在或数量无效时继续回退到生产件数量，重做件仍不触发整单完成状态同步。
